Upstream `e3e5c9da` ("fix(knowledge): stop polling callbacks after subscription close") — `_safe_fire` returns
early when `_closed`, so a callback in flight when the subscription closes does not let the rest of the batch
through. Parity, not a deviation: no DECISIONS entry, no MIGRATION section, public API unchanged.

**Deadlock check (ticket step 2).** `isClosed` takes `w.mu`; the dispatch loop holds `w.mu` only inside
`snapshot()`/`setSnapshot()`, which release it before `safeFire` runs, so `safeFire` → `isClosed` cannot deadlock
against `Close`. No snapshot-copy refactor was needed.

Test seam: a `versionSource` implementing `VersionSource` whose snapshot the test sets atomically — no store writes
race the tick, no `time.Sleep` anywhere; the batch is synchronised with channels (`inFirst` / `release`) and a
bounded wait on `w.isClosed()`. Python's in-callback `close()` has no Go twin: our `Close` waits for the polling
goroutine (`<-done`), so a callback calling `Close` on itself would block on itself — the test closes from a second
goroutine, which is the same interleaving.

# Round 2 — self-close hang (reviewer's return, risk 2 × 3 = 6)

The reviewer took the `safeFire` guard and returned the pre-existing hang noted above: a callback calling `Close()`
on its own watcher waited forever (`Close` waits `<-done`; `done` is closed by the same goroutine sitting in the
callback). Python does not hang in that scenario: `PollingChangeWatcher.close` cancels its task and awaits it, and
awaited from inside that task the cancellation raises immediately (`contextlib.suppress(CancelledError)`), so it
never waits for itself to finish.

## What changed (round 2)

| Step | Change | Files |
|---|---|---|
| 1 | Red test: callback calls `w.Close()` directly (on the polling goroutine); watchdog timeout in the test plus a full goroutine dump; after the fix it asserts one delivery, `w.done` closed, silence afterwards | `knowledge/polling_close_test.go` |
| 2 | `loop` records its goroutine id in `loopID`; `Close` skips the `<-done` join only when it is running on that goroutine | `knowledge/polling.go` |

Mechanism: stdlib exposes no goroutine identity, so `goroutineID()` parses the `goroutine N [running]:` header of a
one-goroutine stack dump. It is read only in `loop` (once) and in `Close` (on shutdown), never on the poll path. A
recycled id cannot misfire: `loopID` is set only while the loop can still be running, and once that goroutine exits
`done` is already closed, so a join would return immediately anyway. External `Close` keeps joining the polling
goroutine — the guarantee "after `Close` returns no polling is in flight" is intact for every caller except the
polling goroutine itself.

**Contract vs Python.** Parity, so no `// AGO-DEVIATION` and no DECISIONS entry (next free number would be D-135;
D-134 belongs to ticket 014): after `Close` from a callback, delivery stops with that callback and the polling
goroutine exits as soon as it returns — the same observable end state as Python cancelling its own task. Public API
unchanged.

# Round 3 — the join itself was untested (reviewer's second return)

The goroutine-id mechanism was accepted, `Close` stays as it is. Three gaps:

1. **Mutation M2 survived:** with `self := true` (Close never joins) the whole suite stayed green — nothing
   asserted that an external `Close` actually waits for an in-flight callback.
2. The `goroutineID` comment did not say what happens when the header fails to parse.
3. The `acp` flake from round 2 was not written down.

## 1. New test, M2 killed (artifacts `m2.txt`, `m2-count10.txt`)

`TestPollingWatcherCloseFromCallerWaitsForCallback`: two changed paths; the first delivery blocks on `release`,
then on `finish`, and only then stores an `atomic.Bool` "returned". The test starts `Close` on another goroutine,
waits until the flag is set, opens `release`, and then requires that `Close` **cannot** return while `finish` is
still closed off — a bounded probe (`joinProbe` = 200 ms, `time.After`, no `time.Sleep`) proves the negative; a
joining `Close` cannot return at all before the callback ends. Then `finish` opens, `Close` must return, and the
`atomic.Bool` must read true; one delivery, no more.

Mutation M2 — `self := w.loopID != 0 && w.loopID == goroutineID()` replaced by `self := true`:

```
--- PASS: TestPollingWatcherCloseStopsBatchDispatch (0.30s)
--- PASS: TestPollingWatcherCloseFromCallback (0.30s)
--- FAIL: TestPollingWatcherCloseFromCallerWaitsForCallback (0.06s)
    polling_close_test.go:264: Close returned while the callback was still running: it did not join the polling goroutine
```

Repeated under the same mutation, `-count=10`: 10 of 10 runs red with that exact message (`m2-count10.txt`,
`FAIL github.com/luckystrker/ago/knowledge 0.549s`). Without the mutation the test is green and the count is part
of the 20/20 run below. Note the other two tests passing under M2 is exactly the reviewer's finding: they never
observed the join.

## 2. `goroutineID` comment

Now records the failure mode: parsing returns 0, which equals no live goroutine, so `Close` joins as usual — a
callback closing its own watcher blocks on itself again, and so does a `Close` from another goroutine that the
callback waits for. A hang at shutdown, never a crash or a wrong callback.

## 3. `docs/known-issues.md`

Added `acp/TestProviderStartupFailures/exits_during_the_handshake` to "Flaky tests": fake agent exits during the
handshake, the `initialize` write hits the closed pipe and surfaces as `acp: write: write |1: broken pipe` instead
of a transport error wrapping `ErrAgentExited`; reviewer measured 2 of 200 under `-count=200`, executor saw it once
and could not reproduce it. Risk 2 × 3 = 6, so it is queued for its own ticket rather than left open by choice;
expected fix — map `EPIPE` on a handshake write onto `ErrAgentExited`. `acp` code untouched.
